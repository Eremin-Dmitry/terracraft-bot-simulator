# Возможные улучшения алгоритма бота

Исходный алгоритм Алисы прост и предсказуем: бот исследует комнаты по минимальным номерам, собирает самый ценный ресурс в каждой комнате, а затем возвращается в стартовую комнату кратчайшим путём. Такой подход легко реализовать, но он не всегда максимизирует суммарную ценность ресурсов.

## 1. Учитывать ценность пути, а не только номер комнаты

В текущем алгоритме бот выбирает соседнюю непосещённую комнату с наименьшим номером. Это может привести к тому, что бот потратит еду на малополезную ветку подземелья и не успеет попасть в комнату с дорогими ресурсами.

Улучшение: выбирать следующую комнату по ожидаемой выгоде. Например, можно оценивать отношение предполагаемой ценности ресурсов к стоимости пути.

Плюсы:

- бот чаще будет идти к более ценным комнатам;
- целевой ресурс будет собираться приоритетнее;
- результат станет лучше на графах с неравномерным распределением ресурсов.

Минусы:

- в видимых комнатах ресурсы неизвестны, поэтому оценка может быть неточной;
- алгоритм станет сложнее;
- потребуется аккуратно учитывать запас еды на возвращение.

## 2. Всегда резервировать еду на возвращение

В исходном алгоритме фаза исследования ограничена половиной еды. Это безопасное, но грубое правило. В некоторых подземельях путь назад короткий, и бот мог бы исследовать больше комнат. В других случаях половины еды может быть недостаточно, если бот ушёл далеко по длинному коридору.

Улучшение: после каждого шага пересчитывать кратчайший путь до старта и не выполнять действие, если после него не останется еды на возвращение.

Плюсы:

- бот использует запас еды эффективнее;
- можно исследовать больше комнат в компактных графах;
- снижается риск оказаться далеко от старта без еды.

Минусы:

- требуется чаще запускать поиск кратчайшего пути;
- на больших графах вычисления станут дороже, хотя для ограничения 255 комнат это не критично.

## 3. Собирать не только один ресурс в комнате

Сейчас в фазе исследования бот собирает только самый ценный ресурс в комнате. Но иногда выгоднее потратить одну дополнительную единицу еды на второй ресурс, чем идти в новую комнату.

Улучшение: перед выходом из комнаты оценивать, стоит ли собрать дополнительный ресурс. Решение можно принимать по сравнению ценности ресурса и стоимости альтернативного маршрута.

Плюсы:

- бот лучше использует комнаты с несколькими ценными ресурсами;
- особенно полезно, если в комнате есть целевой ресурс и gems/gold;
- может повысить итоговую ценность без дополнительного перемещения.

Минусы:

- дополнительный сбор тратит еду;
- если потратить еду слишком рано, можно не успеть исследовать более выгодную комнату.

## 4. Использовать жадную оценку `value / cost`

Для каждой достижимой комнаты можно считать примерную оценку:

```text
score = expected_resource_value / path_cost
```

Затем выбирать комнату с максимальным score, а при равенстве — с меньшим номером.

Плюсы:

- простая и понятная эвристика;
- хорошо работает, когда ресурсы в посещённых комнатах уже известны;
- легко объяснить и протестировать.

Минусы:

- не гарантирует глобальный максимум;
- может выбрать близкую комнату со средней выгодой вместо дальней комнаты с большой выгодой.

## 5. Планирование через динамическое программирование

Если считать, что вся карта известна симулятору, можно построить более сильный алгоритм: состояние включает текущую комнату, оставшуюся еду и набор собранных ресурсов. Далее можно искать путь с максимальной суммарной ценностью.

Плюсы:

- можно получить близкое к оптимальному или оптимальное решение;
- хорошо подходит для сравнения с простым алгоритмом Алисы;
- помогает оценить качество эвристик.

Минусы:

- пространство состояний быстро растёт;
- полный перебор собранных ресурсов может быть слишком дорогим;
- такой алгоритм хуже соответствует условию, где карта изначально неизвестна персонажу.

## 6. Разделить стратегию и симулятор

Текущий проект уже отделяет модель подземелья и класс бота. Дальше можно выделить интерфейс стратегии, например `IBotStrategy`, чтобы подключать разные алгоритмы без изменения симулятора.

Плюсы:

- удобно тестировать несколько алгоритмов;
- можно сравнивать простой алгоритм, жадный алгоритм и оптимизатор;
- код становится ближе к промышленной архитектуре.

Минусы:

- появляется больше файлов и абстракций;
- для маленького задания это может выглядеть избыточно.

## Итог

Самое практичное улучшение — не жёстко тратить половину еды на исследование, а после каждого действия проверять, сколько еды нужно для возвращения. Второе полезное улучшение — выбирать следующую комнату по ожидаемой выгоде, а не только по минимальному номеру. Эти изменения относительно простые, но уже могут заметно увеличить итоговую ценность собранных ресурсов.
